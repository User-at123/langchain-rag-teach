================================================================
LangChain 教学项目 · 可改进方向与思路笔记
（基于当前项目：DeepSeek + bge-small-zh 本地嵌入 + Chroma 持久化向量库）
================================================================

一、大数据量知识库：加载与切分的提速方案
----------------------------------------------------------------
当前瓶颈：
- 整个文件 open() 一次读入内存，数据量大时直接内存爆掉
- 切分后全部存内存向量库（InMemoryVectorStore），只适合几百条以下，而且会随着电脑重启向量索引消失。
未来如果数据量变大，会导致每次启动时间花费巨大。

改进方向（按性价比排序）：
1. 换持久化向量库
   - FAISS（本地单机，轻量，pip 直接装）
   - Chroma（本地，自带简单管理）
   - 规模更大：Milvus / pgvector / Elasticsearch
   - 教学建议：先升级 FAISS 或 Chroma，改一行代码级别的成本

2. 批量加载，不要一次读入
   - 用 LangChain 的文档加载器按目录批量加载：
     DirectoryLoader / PyPDFLoader / CSVLoader / JSONLoader
   - 每种格式用对应的 Loader，而不是自己 open() 解析
   - 注意：新版 langchain-community（0.4+）已移除 DirectoryLoader 的 loader_map 参数，
     本项目已改为手动 os.walk 遍历 + LOADER_MAP 路由（见第五部分第 2 步）

3. 更优的切分策略（Chunking 优化指南）
   【切分大小的影响】
   - 切太细（如 50 字）：语义断裂。"星辰科技成立于2015年"被切成两块，
     问"哪年成立"只命中一半 -> 答错
   - 切太粗（如 1000 字）：一个块塞多个不相关主题，向量被稀释，
     区分度差 -> 噪声大，答不准
   - 经验值：中文一般 200~800 字，chunk_overlap 防止一句话卡在边界被切断
   - 判断方法：切完打印几个块看看——"一句话被拦腰切断"就调大 overlap；
     "一个块里话题混杂"就调小 chunk_size
   - 注意：改参数后必须删 chroma_db 重建索引才生效

   【不同格式的切分器对照】（本项目 2.5 步已实现其中 Markdown 与表格两项）
   | 内容类型 | 推荐切分器 | 优势 |
   | 普通文章/文档 | RecursiveCharacterTextSplitter | 通用够用（本项目现状：txt/pdf/docx） |
   | Markdown/结构化 | MarkdownHeaderTextSplitter | 按标题层级切，章节不拆散（本项目已实现：.md） |
   | 代码 | CodeSplitter | 按函数/类边界切 |
   | PDF（有章节标题） | 先解析结构再按标题切 | 保留章节层级 |
   | 表格/数据 | 一行或一个记录为一块 | 表格语义在"行"（本项目已实现：.csv/.xlsx 按行入库） |
   | 语义敏感文本 | SemanticChunker | 按语义边界切，块内主题一致，最慢但最好 |
   | 任意（进阶） | ParentDocumentRetriever | 小片段检索（精准）+ 大段落上下文（完整） |

   【切分与检索质量的关系】
   - 检索质量 = 嵌入模型质量 x 切分质量 x 检索算法
   - 切分决定"检索的最小单元"：命中准不准看块内是否完整语义；
     答得全不全看返回块是否包含完整上下文
   - 没有绝对最优参数，需要实验调参
   - 第 3 步的 BM25 + 重排序可在一定程度上弥补切分不完美（先广召回再精排）

   【当前项目的实验方法】
   - 改 rag.py 中 splitter 参数后删 chroma_db 重建索引：
     splitter = RecursiveCharacterTextSplitter(chunk_size=100, chunk_overlap=20)  # 更细
     splitter = RecursiveCharacterTextSplitter(chunk_size=400, chunk_overlap=100) # 更粗
   - 用同一批问题分别测试，对比回答质量

4. 检索质量增强
   - 混合检索：BM25 关键词检索 + 向量相似度检索，取并集再融合
   - 重排序（Rerank）：第一轮召回 Top50，用 bge-reranker 精排取 Top3，
     能显著提升命中准确率
   - 元数据过滤：给每篇文档打标签（部门/年份/类型），检索前先过滤，
     既快又准

5. 索引的增量更新
   - 知识库经常变化时，用 LangChain Indexing API 只处理新增/变更的文档，
     避免每次全量重建
   - 生产环境可用定时任务（如每天夜里重建索引）

二、多模态知识库：文字 + 视频 + 图片 + PDF
----------------------------------------------------------------
核心思路：把一切内容先"转成文本"，再进同一个 RAG 流程。

1. 视频内容怎么进知识库
   - 步骤：抽音频 -> 语音转文字(ASR) -> 转写文本当普通文档切分入库
   - 工具推荐：
     * 本地：faster-whisper（免费、离线、中文效果好）
     * 云端 API：阿里/讯飞/腾讯语音转写
   - 进阶：转写时保留时间戳，chunk 里带上时间点，
     这样回答时可以定位到视频第几分钟，方便跳转核对
   - 如果视频有字幕（srt 文件），直接解析字幕文本即可，最简单

2. 图片内容怎么进知识库
   - 方案 A（推荐）：图片 -> 视觉模型（Qwen-VL 等）生成文字描述 -> 入库
   - 方案 B：CLIP 类模型把图片和文字映射到同一向量空间，可直接图文互搜，
     适合"找相似图片"的场景
   - 公司海报/截图/扫描件：先 OCR（PaddleOCR）提取文字再入库

3. PDF / 表格 / 复杂排版
   - 用 unstructured 或 PyMuPDF 解析，保留表格结构和段落顺序，
     避免整页硬切导致语义断裂

4. 统一入口
   - 无论文字/视频/图片，最终都变成"文本块 + 元数据(来源、类型、时间)"，
     存进同一个向量库，检索时通过元数据区分模态

三、基于知识库做内容创作：海报、文案、建议
----------------------------------------------------------------
思路：RAG 负责"提供准确的公司素材"，生成环节负责"创作"。

1. 生成海报图片（3 种路线，由易到难）
   - 路线 A：LLM 生成文案 -> 调用绘图 API
     * 通义万相 / 文心一格 / Stable Diffusion 等文生图服务
     * 提示词 = RAG 检索到的产品卖点 + 设计风格要求
   - 路线 B（推荐做公司定制海报）：LLM 生成 HTML/CSS 模板
     -> Playwright 无头浏览器截图
     * 优点：可套公司统一模板、字体、logo，输出可编辑
   - 路线 C：程序化排版：PIL / ReportLab 按模板生成图文

2. 文案类创作（海报文案、公众号、营销话术）
   - 提示词里注入：检索到的产品资料 + 目标人群 + 平台风格
   - 注意：让 LLM 引用检索到的"事实"（如参数、价格、案例），
     创作类内容反而要给它自由度

3. 给出使用者建议（个性化推荐）
   - 做法：把用户的问题/画像也向量化，检索相关知识 ->
     让 LLM 结合资料生成针对性建议（类似"顾问模式"）
   - 进阶：沉淀用户偏好 -> 形成用户画像 -> 检索时加权

4. 公司素材（logo 等）的存储规范
   - 原则：logo 是公司静态资产，存文件系统/对象存储，不存数据库 BLOB
   - 存储位置按项目阶段划分：
     * 当前（本地教学）：项目内 assets/logo/ 目录
       PythonProject1/
       ├── assets/
       │   └── logo/
       │       ├── company_logo.png    # 透明底 PNG，合成到生成图上
       │       └── company_logo.svg    # 矢量版，报表/打印无损缩放
     * 部署后（FastAPI 服务）：云对象存储（阿里 OSS / 腾讯 COS / AWS S3），
       代码里存 URL，多实例共享 + 可挂 CDN
     * 配置方式：.env 中加 LOGO_URL=https://your-bucket.../logo.png
   - 格式建议：至少存两份（透明底 PNG + 矢量 SVG）；原始设计稿单独备份
   - 生成图片时 logo 的正确用法（关键）：
     * 不要让 AI 模型"画"logo——模型画的公司 logo 一定不准
     * 正确做法：AI 生成主体内容 + 程序化叠加真实 logo 文件
     * 按生成路线区分：
       - HTML/CSS 模板截图：logo 作为 <img> 嵌进模板（最自然）
       - 文生图 API：用 PIL 把 logo 贴到生成的图上（角落、控制透明度）
       - PIL/ReportLab 排版：直接读取 PNG 贴入
   - 注意细节：
     * 权限：对外用户与内部用户区分"带水印版/原图"
     * 备份：logo 原文件单独备份，大体积二进制不提交 git 仓库
     * 版本：文件名带版本号（logo_v2.png），公司换 logo 时历史素材仍可用

四、整体架构演进（从小脚本到产品）
----------------------------------------------------------------
1. 封装成服务：FastAPI 包一层 API，网页/小程序/IM 都能调
2. 加对话记忆：记住上下文，支持多轮追问（HistoryAwareRetriever）
3. 升级成 Agent：让模型能调用工具（查数据库、生成图片、发邮件），
   主动完成多步任务
4. 质量评估：用 RAGAS 之类的指标评估检索+生成质量，别凭感觉调参
5. 权限与安全：不同部门只能检索自己权限内的知识（元数据 + 权限过滤）

五、当前项目的最小升级路径（建议顺序）
----------------------------------------------------------------
[已完成] 第 1 步：InMemoryVectorStore -> Chroma
   - 已在 rag.py 实施：索引落盘到 ./chroma_db，首次运行创建、之后直接加载，chroma_db中存储数据被切后的数据（元数据）以及向量数据和其对应的文本块。
   - 若想换 FAISS：pip install faiss-cpu langchain-community，
     用 FAISS.from_texts(chunks, embedding) + save_local / load_local
   -如果以后想修改knowledge_base.txt，必须修改完成之后手动删除索引重建,代码为;
   Remove-Item -Recurse -Force chroma_db

[已完成] 第 2 步：多格式加载（第一阶段）
   - 已在 rag.py 实施：docs/ 目录 + os.walk 手动遍历 + LOADER_MAP 按扩展名路由
   - 背景：新版 langchain-community（0.4+）移除了 DirectoryLoader 的 loader_map 参数，
     故改为自己写循环遍历目录（for root, _, files in os.walk），不依赖框架版本 API
   - LOADER_MAP 结构：(Loader 类, 参数)，如 .txt/.md -> TextLoader(encoding="utf-8")
   - 支持 .txt / .md / .pdf / .docx / .csv，不支持的类型打印提示并跳过
   - 编码：文本类 Loader 显式传 encoding="utf-8"，避免 Windows 默认 GBK 解码中文报错
     （UnicodeDecodeError: 'gbk' codec can't decode byte ...）
   - 切分统一用 RecursiveCharacterTextSplitter，split_documents 保留来源 metadata
   - 回答时标注来源（format_docs 读取 metadata["source"]）
   - 说明：当时的已知边界（.xlsx 需另存为 CSV、切分策略未按格式区分）已在 2.5 步解决
   - 注意：docs/ 有文件时优先加载 docs/；为空时回退 knowledge_base.txt

[已完成] 第 2.5 步：多格式切分差异化（第二阶段）
   - 已在 rag.py 实施：切分阶段按扩展名路由切分器（split_documents_by_format）
     * .md   -> MarkdownHeaderTextSplitter：按 #/##/### 标题层级切，标题保留、章节不拆散；
                （注意：该切分器输入是字符串而非 Document，切出的块需手动补回 metadata["source"]）
     * .csv/.xlsx -> 表格语义在"行"：加载时已按行拆成单个 Document，切分阶段直接透传不再切
     * 其他（.txt/.pdf/.docx）-> RecursiveCharacterTextSplitter（chunk_size=200, chunk_overlap=50，保留）
   - 原生 .xlsx 支持：不用 LangChain 的 UnstructuredExcelLoader（需重量级 unstructured 依赖），
     用 openpyxl 自写 load_xlsx：每行一个 Document、单元格用 | 连接、跳过全空行、
     metadata["source"] 标注「工作表名 + 行号」（如 "sample.xlsx [工作表: 产品价格表 第2行]"）
   - 新增依赖：openpyxl
   - 验证方式：删 chroma_db 重建后，用 chromadb 直接读索引（不联网、不加载嵌入模型，
     避免 HuggingFaceEmbeddings 初始化联网卡死）确认 sample.md 按标题切成 4 块、
     sample.xlsx 按行入库 8 条（产品价格表 4 行 + 客户案例 4 行，含表头行，2.6 步已改进）
[已完成] 第 2.6 步：xlsx 表头拼接（修复"问字段名拿不到值"的 bug）
   - 背景：2.5 步按行切表后，表头行（字段名）和数据行（值）被拆成不同 Document，
     问"客户行业是什么"时检索命中表头行——只有字段名没有值，答"具体内容未显示"
   - 已在 rag.py 实施：load_xlsx 升级——第 1 行视为表头，数据行拼接为
     "字段名: 值 | 字段名: 值"（如 "客户行业: 金融 | 客户名称: 华信银行 | ..."），
     表头不再单独入库；跳过全空行、跳过与表头重复的行；
     无表头的表（表头全空）退化为原 | 连接行为
   - 原理：让数据行"自包含"字段名，检索命中数据行就能直接拿到值，不用跨块猜
   - 验证结果：加载 7 个文档（md 1 + xlsx 6）、切分 10 个片段（md 4 + xlsx 6）；
     问"客户行业有哪些"正确回答"华信银行，所属行业：金融"
   - 注意：加载/切分逻辑变化后必须删 chroma_db 重建索引才生效
[已完成] 第 2.7 步：检索参数调优（修复"列举类问题答不全"）
   - 背景：检索器 k=2 只返回最相关 2 个片段，问"所有客户的行业"只召回 1 条案例行，
     模型答"仅有一条客户案例：华信银行（金融）"
   - 试错：先试 MMR 检索（search_type="mmr", k=3, fetch_k=20）——它按"相关+多样"平衡，
     把结构相似的 3 条客户案例行当"重复"去重只留 1 条，多出的名额给了 md 里无关块，仍答不全
   - 定稿：普通相似度检索 + k=6，3 条案例行相关性都高，全部进候选
   - 验证：问"所有客户的行业有哪些？" → 完整列出华信银行（金融）、优品超市（零售）、明德学院（教育）
   - 注意：检索参数变化**不需要**重建 chroma_db（只影响查询，不影响索引内容）
   - 与第 3 步的关系：数据量变大后靠调大 k 会引入噪声，需 BM25 混合检索广召回 + reranker 精排
   - 已知边界（V7.8 记录，暂不改代码）：k=6 只是当前 10 个片段知识库的调优值，不是通用解。
     "列举所有 / 汇总 / 统计"类问题需要全量访问，不属于 Top-k 检索的舒适区。
     一万客户时两种崩法：k 太小漏召回；k 调到 1 万则提示词 token 超限 + 检索噪声爆炸。
     三档正解：整表引用（几百行）→ 分批聚合（几千~几万行）→ 结构化 RAG / Text-to-SQL
     （生产级 1 万+：客户数据进数据库，问题转 SQL 返回聚合结果，向量检索只负责定位哪张表/哪个条件）。
     结论：k=6 保留为"事实查询"教学配置；数据量真实增长到万级时走 Text-to-SQL 升级
   - 第二类边界（引用前面结果的推理，V7.8 补充）：第 1 轮"所有客户信息"走 SQL 全量导出，
     第 2 轮"基于刚才导出的第 3 条分析"——这是对上一轮结构化结果的推理，
     知识库里没有这个中间结果，走向量检索必然命中不了；正确路径是会话记忆 + 跨轮状态（第 9 步）
[已完成] 第 3 步：BM25 混合检索 + bge-reranker 重排序（第三阶段）
   - 已在 rag.py 实施：单一向量检索 → 三环节流水线
     BM25 关键词检索（jieba 分词）→ 向量检索 → RRF 融合 → bge-reranker 精排 Top 6
   - 架构变化：k 从"回答视野"（V7.7 的 k=6）降级为"粗筛漏斗"——
     两路都召回 50，精排后只留 6 条进提示词（最终视野仍承接 V7.7 的 k=6 经验）
   - 手写实现（重要教学决策）：官方 EnsembleRetriever / CrossEncoderReranker 在独立包
     langchain-retrievers，但国内镜像（清华/阿里）未同步、PyPI 也无法安装 → 装不上；
     改为手写两个类（各约 20 行）：RRFRetriever（互惠排名融合）+ RerankerRetriever
     （sentence-transformers CrossEncoder 懒加载）——教学价值反而更高
   - 踩坑 1：rank_bm25 默认按空格分词，中文整句成一个 token，BM25 直接失效
     → 必须传 jieba 分词器：preprocess_func=lambda t: list(jieba.cut(t))
   - 踩坑 2：本项目 langchain-community 版 BM25Retriever 参数名是 preprocess_func，
     不是新版独立包的 tokenizer（照抄新版文档会报 TypeError）
   - 踩坑 3：reranker 模型首次运行才下载（懒加载），import 阶段不会联网卡住
   - 验证结果：
     * BM25 问"华信银行"精准命中金融案例行；向量问"给零售客户推荐什么"语义命中优品超市
     * RRF 融合后 3 条客户案例行全部进 Top 候选
     * bge-reranker 精排后 3 条案例行稳居前 3，噪声（主营/团队介绍）被压后
     * 回归：问"所有客户的行业有哪些？" → 零售、金融、教育 ✅
   - 新增依赖：rank-bm25（BM25 算法）、jieba（中文分词）
   - 注意：检索参数变化不需要重建 chroma_db；reranker 模型首次运行自动下载
   - 与 SQL 的关系：本步只让"事实查询"更准，**替代不了 SQL**——
     全量列举/统计类问题照样 token 超限，仍走第 5 步（见 mindmap 核心概念 6"检索 vs 查询"）
[待做] 第 4 步：视频字幕/语音转写接入，先做最简单的 srt 解析
[待做] 第 5 步：Text-to-SQL + 路由器（智能分流：向量检索 vs SQL 查询）
   - 为什么排在 FastAPI 之前：封装应一次到位暴露完整能力；先封装纯向量版、
     后面再加 SQL 会导致接口和前端返工（"列举/统计"类问题必须走 SQL）
   - 数据库：先用 SQLite 起步（零配置、单文件，Python 内置 sqlite3），
     把 sample.xlsx 导入客户表/产品表；跑通后换 MySQL 只改连接串（SQL 语法一致）
   - 架构：LLM 路由器判断问题类型（RunnableBranch 二选一）→
     事实查询走向量链（Chroma）→ 列举/聚合/统计走 SQL 链
     （Text-to-SQL：提示词让模型把问题转成 SQL → 执行 → 结果格式化）
   - 用户视角：只暴露单一入口（门面模式），用户不知道后端有几个库；
     FastAPI 阶段依然是 POST /ask 一个接口
   - 安全：LLM 生成的 SQL 只允许 SELECT（只读白名单/最小权限），防止注入
   - 承接：V7.8 认知边界中"列举/聚合类问题 ≠ Top-k 检索"的生产级正解

[待做] 第 9 步：多轮记忆 + 跨轮状态（支撑"引用前面结果的推理"）
   - 背景（V7.8 认知边界补充）：第 1 轮"所有客户信息"走 SQL 全量导出，
     第 2 轮"基于刚才导出的第 3 条分析"——这是对上一轮结构化结果的推理，
     知识库里没有这个中间结果，走向量检索必然命中不了；正确路径是 memory/状态
   - 会话记忆：session_id + ChatMessageHistory，记住"上轮问了什么、答了什么"，
     追问时带上历史（HistoryAwareRetriever 解决"改写追问"，这里解决"引用上轮结果"）
   - 跨轮状态管理：SQL 导出的结果暂存会话状态，路由优先查状态，
     用户说"基于刚才的第 3 条"时直接从状态取，不再重复查库
   - 路由器升级为三路：vector（事实查询）/ sql（列举统计）/ memory（引用上轮结果）
   - 顺序：先在 CLI 验证（不带 FastAPI），跑通后再接入第 6 步的 FastAPI
